# 旧版大屏 dashboard.html 长期维护与冻结策略 (Legacy Dashboard Freeze Policy)

本文件规定了 MAP 项目中根目录下旧版单文件大屏 `dashboard.html` 的长期维护策略、演进边界、修改红线、验收规范及发布回归指南，旨在确保项目在全面迈向 React 主力前端时代的同时，依然维持高质量的 Legacy 对照与低成本安全兜底。

---

## 1. 核心定位与设计原则

随着系统完成 React 现代化架构迁移（即以 `frontend/` 为核心的 React 18 + TypeScript + Vite 前端），旧版 `dashboard.html` 单文件大屏的定位已发生本质变化：

1. **Frozen Baseline / Legacy Fallback（冻结基线 / 灾备回退）**：`dashboard.html` 是已冷冻的底层基线，仅用作数据向下兼容性检测锚点、离线环境下的最低可用参考页面，以及 React 前端和 GitHub Pages 服务发生不可抗力灾阻时的最简备用大屏。
2. **不再承接新功能**：`dashboard.html` **永久不再承担任何新交互特性开发、视觉改版或图表重构的职责**。
3. **零外部依赖原则**：必须永久保持其“零外部网络依赖、单 HTML 文件打包、可纯本地双击离线运行”的核心架构，严禁引入复杂的打包构建工具或外部大体积动态数据拉取库。

---

## 2. 允许修改的生命周期边界

原则上，除了必要的数据更新外，严禁对 `dashboard.html` 进行任何代码层面的修改。唯有在面临以下 5 类例外情况时，经项目组严格评审后允许进行有限度的代码干预：

1. **阻断性运行故障修复**：由于未来主流浏览器内核升级或底层 Web API 弃用，导致旧大屏在现代浏览器上完全无法渲染、加载崩溃或出现重大 JS 运行时错误时；
2. **数据兼容性变更**：当底层客流汇总数据结构（如 `data/latest/metro_stats.json`、`city_assets_index.json` 或 `manifest.json`）由于宏观重构发生不向下兼容的字段增删时，允许对旧大屏中对应的数据解析逻辑进行最低限度的降级或适配适配，保障页面数据不白屏、不溢出；
3. **关键语法错误与安全性漏洞修复**：修复内联 JavaScript 代码中潜在的变量污染、执行错误或经扫描发现的安全合规隐患；
4. **消除 legacy-check 的非预期误报**：当自动化测试由于外部测试环境（如 Chromium/Puppeteer 内核版本升级）发生断言漂移、导致 CI 中 `legacy-check` 任务意外失败时，允许对验收脚本或 HTML 结构属性做微调以消除误报；
5. **必要的静态资源或数据路径引用修正**。

---

## 3. 严格禁止修改的红线边界 (Red Lines)

严禁以任何借口或名义对 `dashboard.html` 实施以下任一类型的修改，违者将无法通过代码审查（Code Review）：

* ❌ **禁止新增页面或任何多路由组件**（严禁将 React 的多页面路由理念移植到旧版）；
* ❌ **禁止新增任何新型交互功能**（如：地铁线路图平移缩放、多城市横向对比、CSV 数据导出、海报保存、链接 Query 分享等）；
* ❌ **禁止新增或替换任何 ECharts 图表模块**（如：客流强度分布、年度里程对比、雷达图多维对比等新图表模块一律禁止进入旧版）；
* ❌ **禁止大规模重构 UI 风格与视觉设计**（严禁为了追求与 React 科技风大屏的一致性，在旧大屏中强行引入毛玻璃拟态、Staggered 动画或复杂 CSS Module 架构）；
* ❌ **禁止与 React 主力前端重复开发**（避免在双端上进行双轨功能开发，杜绝极高的工程维护成本损耗）；
* ❌ **禁止绕过 React 分支直接在旧版实现临时性的业务需求**。

---

## 4. 新功能归属与脱钩规则

1. **新功能唯一归属**：未来所有数据可视化大屏的全新特性与业务演进（如数据质量中心 `/#/data-quality`、城市数据横向交叉对比 `/#/compare`、多维导出与分享等），**一律强制且仅可开发在 `frontend/` 目录的 React 前端项目中**。
2. **双端功能正式脱钩**：旧版大屏与 React 前端在功能完整度上正式并永久脱钩。不再要求、也不再建议双端大屏保持功能对称。旧版大屏仅承诺并永久保留其在 **v1.0.0** 阶段定稿的四大基础能力：
   * ECharts 中国地图散点热力与详情面板联动
   * 34 城市地铁年度日客流总揽柱状排行榜
   * 单城市历史年度趋势变化折线图
   * 极简拼音与汉字城市搜索过滤

---

## 5. 自动化验收与 legacy-check 回归规则

为了守护项目底层质量的生命线，双轨发布流程中对旧版基线的自动化校验与验收要求如下：

### 5.1 自动化质量回归命令
在对数据层做任何修改或触发发布流程前，必须在项目根目录下正常执行并全绿通过以下 legacy 回归校验套件：

* **底层数据校验与 Schema 健全性检查**：
  ```bash
  npm run test:data
  # 或直接运行：python scripts/validate_data.py
  ```
* **旧版大屏一键总验收回归（包含编译/语法 check/真浏览器 E2E）**：
  ```bash
  npm run test:acceptance
  # 或直接运行：python scripts/run_acceptance.py
  ```

### 5.2 远端 CI 安全防线阻断
1. **`legacy-check` 永久保留**：GitHub Actions CI 流水线（`.github/workflows/ci.yml`）中的 `legacy-check` 任务是项目发布的质量阻断门。无论 React 前端如何演进，该 Job 必须被严格保留运行。
2. **零妥协通过断言**：如果由于数据源变动或非预期问题导致 `legacy-check` 失败，**严禁通过“降低断言限制”、“移除特定测试用例”或“在 ci.yml 中注释该 Job”等降低工程标准的方式强行上线**。必须彻底排查并修复旧大屏中的适配故障或脚本报错，保障 CI 100% 绿灯。

---

## 6. 发布校验配合流程

在未来的项目周期中，虽然发布与版本 Tag 打标签以 React 现代化前端的上线效果为核心验收标准，但任何正式版本的发布必须满足 **“新前端功能无瑕疵，旧前端数据与基线无破损”** 的双重标准。

在执行发布时，按以下规范与顺序进行质量闭环：
1. 运行 `npm run test:data` 确保底层数据结构安全；
2. 运行 `npm run test:acceptance` 确认旧大屏未被破坏，基础呈现完好；
3. 进入 `frontend/`，依次跑通静态类型检查 (`typecheck`)、本地编译 (`build`)、静态结构安全性扫描 (`check:static`) 以及 E2E 交互回归 (`test:ui` 与 `test:pages`)；
4. 唯有在上述双轨防线全部合规后，方可打上版本 Tag 并推送至 master 分支自动发布。
